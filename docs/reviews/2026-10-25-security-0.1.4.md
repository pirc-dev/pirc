# Security review of PiRC 0.1.4

Reviewer: Claude Fable 5.1, 2026-10-25, at tag `v0.1.4` (commit `423a21f`),
in the history before this repository opened, which is not published; the
`adapter/` it mentions was retired since.
Read-only; the reviewer's test programs ran against a scratch copy of the
repository and were not kept. The reviewer's host names are replaced by
generic ones here; paths are relative to the repository.

**Status:** findings 1 to 10 and the first info item are fixed in 0.1.5,
each with a test (design section 13, 2026-10-25). The other info items are
not adopted yet.

Context given to the reviewer: a relay may face the internet, directly with
TLS or behind a TLS-terminating proxy; 0.1.4 adds
`PIRC_RELAY_TRUSTED_PROXIES`; anyone can reach the handshake and make
approval requests. Decided trade-offs (plaintext payloads in v1, no
end-to-end encryption, every client sees every host) were out of scope.

Baseline: `go vet` and `go test ./...` in `relay/` and the 51 TypeScript
unit tests passed at `423a21f`.

## Findings, most severe first

### 1. Medium: a malicious host can answer another host's requests in the adapter

`adapter/src/upstream.ts` (`onRouted`), with
`relay/internal/server/server.go` (`routeFromHost` delivers to a client by
key, attached or not).

A malicious enrolled host B learns the adapter's client key, which is on
every `Routed` the adapter sends it. Whenever the adapter asks honest host
A's session for history (on attach, on a sequence gap, on every
`session_sync` from a phone; IDs `h_1`, `h_2`, … in sequence), B routes
from its own session a `History` reply with request ID `h_<n>` to the
adapter. The relay stamps it with B's `SessionRef`, but `onRouted` resolved
replies by `requestId` alone and never compared the session. The reply
satisfied A's request, and the phone showed it as room A's history, which
replaces the room's chat: B could rewrite what the operator sees as A's
conversation, or suppress it with an error. App-originated request IDs are
phone-generated UUIDs; the `h_n` ones were guessable.

Verified with a program that seeds rooms for two hosts, issues
`history(roomA)`, and feeds B's forged reply: room A's callback received it.

Fix: keep where each request went and drop a reply from any other session;
make history request IDs random.

### 2. Medium: an unauthenticated attacker can lock everyone out of login

`relay/internal/server/server.go`: `MaxPendingLogins` = 64, `LoginTimeout`
10 s.

Anyone who can reach `/v1alpha1` opens 64 WebSockets and sends nothing.
Every other peer's upgrade gets HTTP 503 until the timeout frees a slot, and
the attacker re-dials (about 7 connections a second, from one machine).
Connected peers stay up, but after a relay restart, a certificate renewal
or a network blip nobody can reconnect for as long as the attacker likes.
The limit is global, so a proxy in front changes nothing.

Verified with a test: with `MaxPendingLogins=8`, eight idle sockets made a
registered host's dial return 503 until the timeout.

Fix: cap pending logins per address; a short deadline for the first frame;
a global limit that is a multiple of the per-address one.

### 3. Medium: one enrolled host can disconnect every client, repeatedly

`server.go`: `announce` accepted any payload that fits one frame;
`subscribe` queues the whole list at once; `queueBytes` closes a peer above
`SendQueueBytes` (4 × `MaxFrameBytes`).

A compromised host announces five or more sessions of about 16 MiB each (a
real announcement is a few hundred bytes). Each `SubscribeSessions` queues
over 80 MiB to the client at once, past its 64 MiB budget, and the client
is closed as too slow mid-list; it reconnects and is closed again. The same
burst as `SessionUpdated` drops clients already subscribed. One host takes
the adapter and every phone offline until its key is removed, and parks
32 × 16 MiB per connection in relay memory.

Verified with two tests at default limits and a client reading one frame
per 300 ms: the subscribing client got one frame, then close 1013 "too
slow"; the subscribed client got three updates, then 1013.

Fix: a small limit of its own for announcement payloads (64 KiB), refused
with `TOO_LARGE`; consider a per-key cap on connections and stored payload.

### 4. Low to medium: idle HTTP keep-alive connections are never closed

`relay/cmd/pirc-relay/main.go`: `http.Server` had `ReadHeaderTimeout` but
no `IdleTimeout`.

Against a directly exposed relay, an attacker sends `GET /healthz` on many
connections and holds them idle; Go keeps each open, exhausting descriptors
or memory on a small host. Behind a proxy this is the proxy's problem.

Verified with a test: after one request and 13 s idle, the connection
still served a second request.

Fix: set `IdleTimeout`.

### 5. Low to medium: control characters in labels reach the operator's terminal

`relay/internal/registry/registry.go` (`cut` bounds length only),
`relay/cmd/pirc-relay/main.go` (raw `%s` into tabwriter); in the adapter,
`device_name` into its registry and `pirc-adapter list`.

Anyone who can reach the relay sends, without a token,
`Hello{label: "laptop\t<key>\t10.0.0.5\t…\n\x1b[2K…"}`. `pirc-relay
pending` prints a forged row (another host's name, an internal address) and
an escape sequence that erases part of the real one. The key column cannot
be forged, which limits the damage, but everything else on the screen can.
Tokens issued without `--label` take the host's label too.

Verified by running `pirc-relay pending` on a crafted registry and reading
it through `cat -v`. The relay's log is safe: slog quotes values.

Fix: print host-supplied fields escaped, and/or refuse non-printable runes.

### 6. Low: a trusted-proxy prefix that covers peers lets them forge their address

`relay/internal/server/proxy.go`.

With a LAN or loopback listed as a CIDR (`10.0.0.0/8`), a peer at 10.0.5.5
connects through the proxy with its own `X-Forwarded-For: 203.0.113.9`; the
proxy appends 10.0.5.5, the walk treats it as a proxy, and the relay
believes 203.0.113.9. The address decides nothing, so this only misleads
the operator; the docs say to list only proxies.

Verified with a test. Unparsable entries, ports, brackets, zones and empty
entries fall back to the connection's address.

Fix: warn at startup about prefixes wider than one address; unmap
IPv4-mapped prefixes, which as written (`::ffff:10.0.0.0/120`) trusted
nothing.

### 7. Low: `remove` and `reject` accept a one-character key prefix

`approve` enforced 16 characters; the others only non-empty. Ambiguity was
detected, a typo was not. Fix: 16 for all three.

### 8. Low: the once-a-minute bound on request rewrites can be raced

`server.go` (`ask`). The freshness check read the in-memory snapshot,
updated only after the write; connections presenting the same new key at
once each rewrote the file. Found by reading. Fix: check freshness inside
`Registry.Request`, under its lock.

### 9. Low: `Approve` does not check that the key is not already registered

`registry.go`. A duplicate entry (reachable through a restored older
registry whose request outlived a later token enrolment) makes `remove`
fail as ambiguous for every prefix, the full key included. Found by
reading. Fix: look the key up first, as `Redeem` does.

### 10. Low: the adapter parses up to 32 MiB of JSON per message before login

`adapter/src/server.ts`. Any connection may send 32 MiB text messages,
parsed before the login check, with no cap on connections. Found by
reading. Fix: a small limit until logged in, and a cap on connections
logging in.

### Info

- The relay's Welcome always said `pirc-relay/0.0.0`; design section 7
  says it carries the version.
- A removed host that reconnects shows in `pending` like a new one; a note
  that it was removed would stop an absent-minded re-approval.
- The adapter's `GET /mesh/<hash>` is unauthenticated: anyone who knows an
  owner key reads its blob, which lists host keys. As in Remote Pi's relay.
- `relay-client/keys.ts` loads an existing key file without checking its
  mode (it is created 0600 in a 0700 directory).
- A host can name its session after another host's ("laptop: main"); the
  app shows no host per room.

## Checked and found sound

- **Login:** a fresh 32-byte nonce; a domain-separated signature; the key's
  length checked before verifying; the role bound to the registered key;
  128-bit tokens stored as SHA-256, compared in constant time, consumed only
  after proof and under the registry's lock; a key removed during login is
  refused; Hello limited to 4 KiB before login.
- **Routing:** the relay stamps `client_key`; a host may announce, end and
  route only its own sessions; clients cannot announce; hosts cannot
  subscribe or attach; takeover only within one host key. No way found for
  one host to read or take over another's session.
- **Frames:** bounded decoding; text or undecodable frames close the
  connection; oversize frames get 1009; routed frames the relay would
  enlarge past the limit are refused.
- **No payload logging** in the relay, the extension or the adapter.
- **Registry file:** 0700 directory, 0600 files, temporary file and rename
  with a directory sync, a lock; the CLI refuses another user's directory;
  an unreadable registry fails closed; removal takes effect within a second.
- **Approval queue:** hosts only; the key proven before recording; 16
  requests; a 96-bit minimum prefix to approve; tokens unaffected by a full
  queue.
- **Extension:** `/pirc`, `/pirc:*` and pi's built-in commands are refused
  as prompt text, with no whitespace, newline or case variant getting past
  (checked against pi 1.0.0's command matching); configuration and key
  written atomically and 0600; errors kept away from pi; `pi -p` sessions
  never appear.
- **Adapter:** pairing tokens single-use, expiring and hashed; an unpaired
  key sees nothing; mesh writes need a valid owner signature over the exact
  bytes, a matching hash, pairing and a higher version, at most 500 KiB;
  revoked phones dropped within two seconds; room IDs include the host key;
  events are checked against the room's current session; host payloads
  cannot crash it.
- **TLS:** on by default; `wss` verifies certificates; plaintext needs an
  explicit setting; `X-Forwarded-For` ignored unless the connection comes
  from a listed proxy.
- **systemd units** are well sandboxed.

## Verdict

No authentication bypass, key spoofing or cross-host session hijack at the
relay. Keep 0.1.4's trust model, but fix the adapter's reply check (1) and
the three resource-exhaustion paths (2 to 4) before the relay faces the
internet, and escape labels in the CLI (5).
